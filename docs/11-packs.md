# 11 · Packs

A **pack** is an installable bundle of the core as data (CLAUDE.md: data, not code): folders, sheets with fields, groups, views, forms, tab sets and column groups, sub-items, example items, documents and library items, links, automations and dashboards. Installing a pack writes ordinary rows; nothing in the app knows a pack's content. Milestones P1–P7 in docs/06; tables and RPCs in docs/02 §15.

**Product name (16 Nov 2026).** Pack manifests name no product or domain: the rename to Keptrow (docs/14) changed no manifest and no installed pack, and the public `/frameworks` page reads the catalogue under the Keptrow brand.

## Where packs come from

| Source | Becomes |
|---|---|
| `templates/packs/*.json` | Native pack files (the manifest below), e.g. `supplier-management.json` |
| `templates/first-sheet.json` | Wrapped by `templateToPack` (`src/lib/packs/wrap.ts`): key = the template id, refs made from names |
| Wizard starts (`templates/starts.json`) listed in `START_PACKS` | Wrapped by `startToPack`: one sheet, key `start-<id>` (CAPA, Documents and policies). A start's `pack` adds the pack's version, automations and dashboards, and optional requirements with what it adds to their sheets (`requires`, `extends`, `onlyWithout`; the wizard ignores it) |
| `templates/apps/*.json` | An app for the pack it `requires` (docs/13), added to that pack's `apps` by `withApps` |

`repoPacks()` (`src/lib/packs/catalogue.ts`) parses all of them. The seed (`pnpm seed`, `scripts/seed.ts`) writes them into the global `packs` table; the app reads only that table. A version is written once: change a pack, raise its version. In a hosted environment run the seed's catalogue step (or an equivalent service-role job) after a deploy that adds a pack version.

The wizard keeps creating a start's sheet its own way (editors may use it, the person picks name, prefix and columns); the same starts are also offered as packs to owners and admins. The template importer (`src/server/templates/importer.ts`, used by the seeds) installs through `install_pack`.

For a hosted project, `pnpm exec tsx scripts/packs-sql.ts > packs-catalogue.sql` writes the repository's packs as idempotent inserts (`on conflict do nothing`); run it as the database owner after the migrations and after `scripts/frameworks-sql.ts`.

## Words people see

Owner decision (15 Nov 2026, board review A1, A6): people read plain words for packs, while the manifests, their keys, titles and versions stay as written (no version is raised for a wording change). `src/engine/packs/words.ts` (pure, tested over the whole catalogue in `src/lib/packs/catalogue-words.test.ts`) maps them where the server reads the catalogue for people (`readCatalogue`, `readPackVersion`, the setup checklists, the test-mode banner, the activity log sentences and the other pack titles shown):

| Manifest says | People read |
|---|---|
| a title ending "(add-on)", e.g. "ISO/IEC 27001:2022 ISMS (add-on)" | the title without it: "ISO/IEC 27001:2022 ISMS"; the concept is a **standard** |
| "Core registers" (the Core pack's title and running text) | "Shared registers" ("the shared registers" in running text) |
| levels Foundations, Starter, Full | Basic, Recommended, Everything ("the Everything level adds …" in running text) |

The Starter level (the middle of the shared registers' three, the first of a standard's two) reads **Recommended**, never "Standard" (owner decision 15 Nov 2026): "standard" means a standard such as ISO 27001. The level keys (`foundations`, `starter`, `full`) and the manifests do not change; `catalogue-words.test.ts` fails if any level of the catalogue reads Standard.

The rest of this document uses the manifest words (add-on, Core, Starter, Full) because it describes the manifests; quoted screen text below is what the screen shows after the mapping. Sheet, field and automation descriptions an install writes into a workspace are workspace data and are not mapped.

## The manifest

Validated by `packManifestSchema` (`src/lib/packs/manifest.ts`), which extends the sheet template schema and then runs the template's own checks on every sheet.

| Key | Meaning |
|---|---|
| `key` | `^[a-z0-9][a-z0-9-]{0,79}$`, the pack's identity |
| `version` | Semver `1.2.3` |
| `title`, `description` | Shown in Workspace admin › Packs |
| `requires` | `[{ pack, range }]`; ranges `1.2.3`, `^1.2.0`, `~1.2.0`, `>=1.2.0`, `*`. Installing the pack installs a required pack first when it is missing (at the level the pack needs), or raises it to that level; a version out of range blocks. `optional: true`: used when live, never installed for you (Optional requirements below) |
| `people` | Example people by `ref` and `email`; values `$person:<ref>` match the workspace's members by email. Missing people are left out (a warning, never a blocker) |
| `folders` | `[{ ref, name, restricted? }]`. An active folder with the same name is used; otherwise the pack makes one. `restricted: true` (P2) makes a new folder restricted: the installer is listed as an editor (owners always see it) |
| `sheets` | A template sheet (docs/07 Part B: `ref`, `name`, `itemLabel`, `idPrefix`, `groups`, `fields`, `views`, `forms`, `tabs`, `defaultView`, `columnGroups`, `subitems`, `retention`) plus `folder` (a folder ref), `isLibrary`, `register: "documents"`, `restricted` (P2: created restricted, the installer listed as an editor), `uniqueLinks` (two link field keys: one live item per pair of targets, `sheets.settings.uniqueLinkPair`, docs/02) and `items` |
| `sheets[].onlyWithout` | An optional requirement's key: the sheet is made only when that pack is not live (Optional requirements below) |
| `sheets[].fields[].config.targetSheetRef` | A link: a sheet ref of this pack, or `<pack key>:<sheet ref>` of a pack in `requires`, resolved at install through that pack's live install (both ways when that sheet's `extends` adds the inverse field) |
| `sheets[].retention` | `{ personalNames?, rules: [...] }`: retention rules (docs/02 §18) stored in `sheets.settings.retention`, groups named by ref (`groups: ["closed"]`, resolved to ids). Checked: unique ids, the date field exists, `fieldKeys` are fields marked personal data. Periods a pack ships are suggestions: say so in the rule's `note` |
| `sheets[].fields[].config.askWhenAdding` | `true`: the New item dialog asks the field with the name (docs/05 §3.7). The packs set it on their audit registers' key fields (below); an extension never sets it on a column it adds to a shared register |
| `sheets[].forms[].layout.intake`, `layout.fields[].step` | The sheet's **intake form**: its New item dialog asks this form until the sheet chooses otherwise (`sheets.settings.newItemForm`, docs/02); `step` on a question starts a new step of the dialog (a title, or "" for none; never on the first question). At most one intake form per sheet; an add-on cannot make one on a shared register (`extendsProblems`): it ships the form for the sheet to choose |
| `sheets[].fields[].config.personalData` | `true`: the field holds personal data (masked in the log, erasable under retention, docs/02 §18) |
| `sheets[].workflows` | Approval workflows (docs/04 §13) stored in `sheets.settings.workflows`: steps, approvers by a people field of the sheet, a job role or a team **by name** (`{ "kind": "jobRole", "roleName": "Top management" }`; people and ids belong to a workspace and are refused), modes, SLAs, rejection targets, required fields, the step field and the status field with their option ids. Checked against the sheet's fields (`workflowProblems`). A role or team the workspace lacks is not an error: submitting names it ("Give a member the job title Top management") |
| `sheets[].items` | `[{ ref, group, name, values, links: { <link field key>: [<item ref>] }, requirements? }]`: example items, documents of a register, library items. Links name items by ref, never by name. Tokens `$today`, `$in:N`, `$option:<label>`, `$person:<ref>` |
| `sheets[].items[].requirements` | `{ <requirement or control link field key>: ["iso-27001@2022#A.6.3", …] }`: example links into the library of a framework in `frameworks` (requirement keys, docs/12), resolved at install (Frameworks below) |
| `automations` | Template automations plus a `ref`. `sheetRef` (a sheet of the pack, or `<pack>:<sheet>` of a pack in `requires`: an add-on's complaint raises a nonconformity in Core), `groupRef` and a form's `ref` resolve to ids; `jobRole:<name>` / `team:<name>` recipients the workspace lacks are left out and said; an automation that then has nobody to tell is installed off |
| `automations[].subitems` | `true`: the automation belongs to the sheet's sub-items (docs/02 §12), i.e. the hidden child sheet of `sheet` (ref map `sheet:<ref>.subitems`). Its trigger and conditions name the sub-items' field keys; the sheet must have `subitems`, and a form trigger is not allowed. Date triggers fire per sub-item; `{sheet}` in a message is "<sheet> · <sub-items label>" |
| `dashboards` | `[{ ref, name, widgets: [{ ref, type, title, sheetRef?, library?, fieldKey?, conditions?, scope?, days? }] }]`, checked against the widget registry. `scope`: the items the widget looks at before its conditions (a count's "of N"); an add-on's widgets on a Core register take its Standards tag as the scope, so every widget on one register counts the same rows (owner decision, Nov 2026). `library: "<framework>@<version>"` (one of `frameworks`) reads the workspace's library sheet of that framework instead of a sheet of the pack; `sheetRef: "<pack>:<sheet>"` reads a required pack's sheet (an add-on's headline dashboard on the Core registers, usually filtered by its Standards tag) |
| `levels` | Optional, 2–5, lowest first: `[{ key, name, description }]` (Levels below) |
| `level` on folders, sheets, forms, automations, dashboards, extends entries | The lowest level that installs the object; none = every level |
| `frameworks` | `[{ key, version, optional? }]`: framework libraries the pack builds on, adopted at install when missing (Frameworks below). `optional: true` is soft: never adopted for you; example links into it are written only where the workspace has adopted it, and widgets and setup steps may not read it |
| `setup` | `{ title, description, steps }`: the guided setup checklist (Setup below) |
| `apps` | Apps over the pack's sheets, forms and dashboards (docs/13), checked against the pack's refs |
| `system` | `true`: a system pack (the Core registers): its sheets are shared registers ("System board", `sheets.settings.system`) and its fields system columns (`fields.system`) |
| `folders[].domain` | A domain folder of shared registers (`management`, `risk` …): listed under Registers in the side menu in the manifest's order, hidden while it has no live sheet, never reusing a folder of the same name |
| `sheets[].folder` | Also `<pack>:<folder ref>`: a folder of a pack in `requires` (an add-on's sheet in a Core domain) |
| `standard` | `{ id, label, color? }`: the standard an add-on stands for. Its option is added to the Standards field of every sheet it extends, with a saved Table view "<label> view" filtering Standards has any of it. The id is in the pack's namespace |
| `extends` | `[{ pack, sheet, fields?, groups?, views?, forms?, items?, automations?, options?, workflows?, level? }]`: what the pack adds to a sheet of a pack in `requires` (Extends below) |
| `sheets[].kind`, `sheets[].personalData`, `automations[].startInTestMode`, `automations[].advanced`, `automations[].description`, `dashboards[].headline`, `formsNotApplicable` | The pack quality bar's keys (Pack quality bar below) |
| `settings` | Choices a workspace makes for the pack (at install or later) that set defaults in its own sheets through `$setting:<key>.<value>` tokens (Pack settings below) |

ID prefixes are unique inside a pack. When the workspace already uses one, the planner renames it with a number (`SUP-` → `SUP2-`, cutting the stem to stay within 6 characters) and the preview says so.

## Install

1. **Preview** (`previewPack`, owners and admins): the server reads the manifest from the catalogue, takes a snapshot of the workspace (prefixes, folders, installs, members with emails, job roles, teams, last positions) and runs the pure planner `planPackInstall` (`src/engine/packs/plan.ts`). The planner reuses the template planner (`src/engine/templates/plan.ts`) for everything sheet-level and returns operations per object (`create`, `reuse`, `skip`, `conflict`), the preview (counts, folders, sheets, links, renamed prefixes, automation sentences, forms, dashboards, warnings, conflicts) and the rows.
2. **States:** `ready`; `installed` (the same version is installed: every operation is `skip`); `blocked` (another version is installed, a requirement is missing or at the wrong version, a link into another pack, a widget that does not fit, a document that would start approved, a value the template planner refuses).
3. **Install** (`installPack`): plans again from the catalogue and the workspace as they are now (the browser sends only the key and the hash it previewed; a changed manifest is refused) and calls `install_pack`, which writes everything with provenance and the ref map in one transaction and logs `pack.installed`.

## Levels

A pack may offer levels (`levels`, lowest first, e.g. Starter and Full), chosen in the install dialog, which shows what each level creates and what it adds to the one before (`levelSummaries`). Every folder, sheet, form, automation, dashboard and extends entry may name the lowest level that installs it; without one it installs at every level. A required pack is installed (or raised) to what the chosen level needs (`neededLevel` per level, Extends). `manifestAtLevel` (`src/engine/packs/levels.ts`) is the manifest as installed at a level.

- The manifest is checked so that nothing needs a higher level than its own: a sheet's folder and link targets, an automation's sheets (its own and `sheetRef` in actions), a dashboard's widgets, a form after its sheet. A two-way link joins sheets of one level only (a higher level never adds a field to a sheet already installed), so links from a higher level to a lower one are one way.
- `pack_installs.level` (0032) keeps the level installed. Installing a higher level of the same version later is not a new install: the planner plans the level whole, leaves out every row whose ref is already in the install's `ref_map` and points the new rows at the existing ids (`extend_install` in the plan). `install_pack` then adds the rows to the same install, refuses a level already installed or a ref the install already has, merges the ref map and logs `pack.extended` with what the level added. Picking a level at or below the installed one is `installed` (nothing to do).
- Workspace admin › Packs shows the installed level and an "Add Everything" button that opens the dialog on the next level.

## Frameworks a pack builds on

`frameworks: [{ key, version, optional? }]` names framework libraries (docs/12) the pack needs. An `optional` one is never adopted by the install (the preview says "Links its items to the … library you have adopted" when it is there); its example links are written only where it is adopted, like any key the library lacks. A new pack version may name a newer edition; an update then warns that the edition is not adopted and leaves the old library alone (ISO 9001 1.1.0 below). The preview says which are not adopted yet ("Adopts the ISO/IEC 27001:2022 requirement library first"); `installPack` adopts them first with `adopt_framework` (each its own transaction, no controls sheet) and then plans the pack again so it finds the library. The pack's sheets link to library items through `requirement` fields with no target sheet (any library); its widgets read the library with `library`.

Example items may link into a required library by requirement key: `"requirements": { "controls": ["iso-27001@2022#A.6.3", "iso-27001@2022#A.8.7"] }` on a risk (the field a `requirement` or `controllink` field of the sheet; the key's framework one of `frameworks`, checked by the manifest schema). `planInstall` reads the adopted library's live items with those `requirement_ref`s (`PackSnapshot.requirementItems`) and the planner writes the links with the install, so the requirement (and the SoA) shows the linked risks at once. Before the library is adopted (the preview) the links are left for the install, which adopts first and plans again; a key the library does not have is left out with a warning, never a blocker. `install_pack` (0033) accepts a link whose target is outside the plan only through a requirement or control link field and only to a live item of a live library sheet of the same workspace. A higher level never writes such a link again (its item and field are already installed).

## Setup

`setup` is a checklist shown after install on Workspace admin › Packs (all steps) and as a dismissible card on Home (the next step; dismissing is kept per browser). Each step has a `ref`, a title, a short own-words body, a `target` (a pack sheet by `sheetRef`, a required pack's sheet by `<pack>:<sheet>` (an add-on's step on a Core register, read through that pack's live install; the fields its rules read count as uses, checked against that pack by `extendsAgainst`) or a required library by `library`, optionally a saved view or a form of that sheet by name: the link opens it, a form in the Forms tab) and `rules`. A step may reword itself at a level (`levels: { starter: { title, body, target, rules } }`), e.g. "List your processes" when Starter has no asset register.

Progress is computed from data by the pure `setupProgress` (`src/engine/packs/setup.ts`): for each rule, of the items matching `where` (all items when empty), the share that also match `all`, counted against at least `min` items (`matched / max(counted, min)`); conditions use the condition operators by field key. A step's progress is the average of its rules; the checklist's percent is the average of its steps (100 only when every step is done). Sheets the person cannot read count as not started and link nowhere. The checklist is checked at every level: each step names sheets, fields and views that level installs.

## Pack settings

Owner decision (14 Nov 2026, for the NIS2 country rules), built as a general mechanism. A manifest may ship `settings`: choices a workspace makes for the pack, at install (the install dialog) or later (Workspace admin › Packs › the pack's **Settings**), that set **defaults in the pack's own sheets**. The choices are data in the manifest (`src/engine/packs/settings.ts`, pure).

- **Manifest:** `settings: [{ key, label, description, values: [{ key, label }], choices: [{ id, label, group?, values: { <value key>: text }, verified, checkedOn?, note?, sources: [{ title, url }] }], default? }]` (at most 5 settings, 60 choices each). A field default (`config.default`, text and long text fields of the pack's own sheets only) or an example value names a choice's value with the token `$setting:<setting key>.<value key>`, e.g. `"config": { "default": "$setting:country.csirt" }`. Checked by `settingProblems`: unique keys and choice ids, tokens that name a value of a setting, never a token in extends or automations.
- **Install:** the planner resolves the tokens with the choices (`applyPackSettings`): a token without a choice (or whose choice has no such value) is left out, so a default is never a token. `installPack` takes `settings` (unknown keys and choices dropped) and, after `install_pack`, records them with `set_pack_settings` (the plan already wrote the defaults). The Create wizard (owner decision, 14 Nov 2026) asks them in its Details step with the same picker (docs/05 §4 Create): `createBundle` keeps only the pack's settings and choices, plans with them and `create_bundle` records them with `set_pack_settings` inside its transaction (0047), so a refused choice creates nothing. A required pack installed first gets no settings; any setting left unchosen is chosen later in Packs.
- **Later:** `setPackSettings` (owners and admins) works out the new defaults of the install's setting fields (`settingDefaults`, by `field:<sheet>.<key>` in the install's ref map) and calls `set_pack_settings(install, settings, fields)` (0043): known settings and choices only, the install's own live fields only, `config.default` set or cleared, `pack_installs.settings` stored and `pack.settings_changed` logged on the workspace chain with the choices' labels ("Changed the settings of NIS2 cybersecurity (Country of main establishment: Germany): 7 defaults updated."). Field changes are logged by the schema audit. Items keep their values; only new items get the new defaults.
- **UI:** a picker per setting (grouped choices), the chosen entry's values, "Checked against the sources on …" or **"Not verified yet: check these details with the authority before you rely on them."**, the note and the sources (open in a new tab). Installed packs with settings show "Country of main establishment: Norway" (or "Settings not chosen yet") and a Settings button.
- **Upgrades:** a field default a setting changed reads as the client's change and is kept.

## Extends

`extends: [{ pack, sheet, fields?, groups?, views?, forms?, items?, automations?, options?, workflows?, level? }]` adds to a sheet of a pack in `requires` (`src/engine/packs/extend.ts`).

- **Rules (manifest checks, `extendsProblems`):** `pack` is in `requires` and is not the pack itself; one entry per sheet; field keys, group, item and form refs and option ids are in the pack's **namespace** (`namespaceOf`: the key without "-", `iso14001`, or `iso14001_…`); no sub-item fields, library items or automations on sub-items; links of extension items go through a link field the entry adds (to the pack's own items) or through a link field the sheet has (to items this pack adds to that field's target); a two-way link between an own sheet and a required pack's sheet needs its inverse in that sheet's extends; a column an entry adds may link both ways to a column another entry of the pack adds to another required sheet (Supplier management 3.0.0: a supplier's Documents on Core's Suppliers and a document's Suppliers on Core's Documents), and its example items may link to the examples the pack adds there; both entries install at one level (`levelProblems`). `extendsAgainst` checks an extension against the required pack's manifest (the catalogue tests): the sheets, groups and field keys it uses exist and new keys are new.
- **Planning:** each foreign sheet the pack reaches into (extends targets, link targets, action sheets) becomes a virtual sheet of the template (its live columns, with the options added, and groups) so the template planner resolves keys, `$option:` tokens, links, inverses and automations as for the pack's own sheets; then the virtual rows are swapped for the real ids and only what the extension adds is written: columns after the sheet's last (system columns), groups, views (`<pack>:<sheet>.view.<n>`, the standard view `.view.standard`), forms, example items (numbered by that sheet) and links. Options: `options` and the standard's option merge by id (an id already there is left as it is) into `plan.options` (ref map `option:<pack>:<sheet>.<key>.<id>`). A column key the sheet already has is a conflict. The snapshot (`PackSnapshot.foreign`, `foreignFolders`) carries the required installs' live sheets.
- **Reaching into Core from the pack's own objects:** an own automation's `create_item` may name `<pack>:<sheet>` (checked by `extendsProblems`; the keys it sets count in `extensionUses`), a dashboard widget may read `<pack>:<sheet>` (its field and condition keys count too), and an example item an extension adds may link into a required library (`requirements`) through a requirement column the same entry adds (`iso9001_clauses`). While the required pack is still to be installed first, the preview does not check those automations and widgets: the install plans again once it is there.
- **Ownership:** every row an extension adds has the extender's provenance and is in the extender's ref map, so the extender's upgrade and archive touch only its own rows.
- **Install order:** `requiredFirst` lists required packs that are missing or below the level the pack needs at the level being installed; `installPack` (and Create) install them first, each in its own transaction (`installRequired`), then plan the pack again. The preview says "Installs Shared registers 1.1.0 (Recommended) first." and lists what it adds to each register.
- **Upgrades:** an add-on's update adds new columns, groups, views, items and options to the Core sheets as for its own sheets (`upgrade_pack` accepts rows on required packs' sheets). A Core update that removes or retypes a field a live add-on uses (`extensionUses`: keys its views, forms, items, options, automations, formulas and lookups name) or drops a sheet it extends is **blocked**, naming the add-on.
- **Archive of an add-on:** its own sheets, dashboards and automations as for any pack; on the Core sheets its columns are archived (restorable), its views removed, its groups removed when empty (kept with items), its standard's option taken out of the Standards fields (items keep the id; installing again brings the tag back). Options it added elsewhere stay (items may use them). No shared row is deleted: items it added and items tagged with its standard stay with their history. The confirm dialog says so.
- **Approval workflows (`workflows`, 0044):** an add-on may add approval workflows (docs/04 §13) to the extended sheet, ids `<namespace>_…` (never the bare namespace: a workflow people name after the standard stays theirs). Checked against the sheet's fields with the options the entry adds (`extendsAgainst`); the fields a workflow names count as uses. Planned as `plan.workflows` (`<pack>:<sheet>.workflow.<id>`) and merged by id into the sheet's `settings.workflows` by `install_pack` (an id already there is left as it is; only workflows the manifest ships on that sheet, onto a live sheet of a required pack). An upgrade of the add-on compares its own entries (its namespace) as one value and writes the sheet's list with everything else kept in place (`apply_pack_upgrade` refuses any other difference); an upgrade of the required pack leaves the add-ons' entries out of its comparison and keeps them; archiving the add-on takes its entries off (approvals in progress keep their copy).
- **Levels (`level`):** an entry installs from that level of the add-on (`manifestAtLevel`), so an add-on's Starter can need only Core Starter: `neededLevel(m, dep, level)` is computed from what that level installs, and `requiredFirst` installs or raises the required pack to what the chosen level needs (a later level raises it again). Checked by `levelProblems`: an entry's links, link items and actions use only own sheets installed at its level, and a two-way link between an own sheet and the extended sheet has its inverse in an entry of the sheet's level (ISO 9001 2.1.0's External providers ↔ Core Suppliers, Full).
- **Hosted:** apply migrations 0041 and 0044, then load the catalogue (`scripts/packs-sql.ts`).

## Optional requirements

Owner decision (15 Nov 2026): CAPA reuses Core's register. One pack version may work on another pack's registers when that pack is live and on its own sheets when it is not (`src/engine/packs/optional.ts`, pure):

- **Manifest.** `requires: [{ pack, range, optional: true }]` is never installed for you. `sheets[].onlyWithout: <pack>` marks the sheets the pack makes only without it; every optional requirement needs at least one.
- **Two cases, from data** (`manifestFor`, as `manifestAtLevel` for a level). *With the pack live*: the `onlyWithout` sheets are left out with everything that needs them (the closure Create uses when a part is left out: their forms, automations, dashboards, setup steps and app screens) and the requirement is an ordinary one (raised to the level the pack needs). *Without it*: the requirement is dropped with everything that names it (`<pack>:<sheet>` widgets, actions, app screens and setup steps, its `extends` entries). Two apps may share a key when each belongs to one case; an app whose screens a case leaves out is not there.
- **Which case.** A new install takes the case of the workspace: with the pack when it is live, in range or not (out of range blocks with "update it first", never a second register). An install keeps its case: it was made with the pack when its ref map has none of the `onlyWithout` sheets (`installCase`). The planner, the update planner (both versions in the install's case, so an update never moves an install onto another register), the apps (`getApps`), Create and Workspace admin › Packs all read the case this way.
- **Checks.** `optionalProblems`, then every case is checked as a whole manifest (`packManifestSchema`); a problem names its case ("… (with core)").
- **Create.** A set that works on registers the workspace has may make no sheet of its own: the preview says "Works on registers you already have: … No second register is made." and Next is offered.

**CAPA** (`start-capa` 1.2.0, `templates/starts.json` → `pack`): `requires` core ^1.1.0 optional; its own register "Corrective action (CAPA)" is `onlyWithout: core`. With Core live it makes no sheet: it adds the internal draft form "Raise a nonconformity" (`startcapa_report`: when, grade, what is wrong; Stage Containment) to Core's Nonconformities and CAPA, declares Core's Actions, and installs the dashboard "CAPA overview" on Core's registers (open, awaiting verification, by stage, by grade, overdue nonconformities, overdue actions). Its app is `templates/apps/capa-on-core.json` (docs/13). Without Core it is 1.1.0 again (its register, the steps automation, its overview and its app). Same major: a 1.1.0 install updates without a change and keeps its own register, also when Core arrived later (moving its records onto Core's register is not decided). Unit tests `src/lib/packs/capa.test.ts` (1.1.0 is `tests/e2e/fixtures/catalogue/start-capa@1.1.0.json`); e2e `tests/e2e/apps.spec.ts`. Hosted: load the catalogue (`scripts/packs-sql.ts`); no migration.

## Bundles: ready-made sets from Create

The Create wizard's "Solve a problem" (docs/05 §4 Create) offers the catalogue's packs (frameworks excepted) as **ready-made sets**: the same manifest, planner and `install_pack`, with four additions. Owners and admins create them, as for packs; members see the set and its preview with "Ask an admin".

- **Parts.** `bundleParts` (`src/engine/packs/select.ts`, pure) lists the manifest's sheets, forms, automations and dashboards at the chosen level, with what each needs: a form its sheet; an automation its sheet, the sheets its actions name and the form that starts it; a dashboard the sheets its widgets read; a sheet the sheets its link fields point at. Leaving a part out leaves out everything that needs it (`togglePart` says what, and ticking a part brings back what it needs; an add-on's extends entries lose what needs a left-out own sheet: the columns that link to it, roll-ups and lookups through them, and the views, form fields, example values, workflows and automations that name them or act on that sheet); `selectManifest` is the manifest as chosen: those parts gone, folders nobody uses dropped, setup steps on a left-out sheet dropped, the folder choice applied (its own folders, an existing folder by name, which the planner reuses, or none; a pack with a restricted folder keeps its folders). Apps stay as written: a screen whose objects the install lacks is not shown (docs/13). The server closes the exclusions again whatever the browser sent.
- **Safety.** A public form is flagged in the preview (forms install as drafts, so nothing is public until an owner or admin publishes it). An automation with an action that sends data out of the workspace (`OUTBOUND_ACTIONS`: webhook, email) is flagged and installed off whatever the manifest says. The preview says who can see each sheet (restricted ones: you and the owners).
- **Name, owner, review.** `create_bundle(org, plan, { name, owner_id, review_by, settings? })` (0038, settings 0047) runs `install_pack` and stamps the install with `bundle_name`, `owner_id`, `review_by` and `origin = 'create'` in the same transaction, then logs `bundle.created` on the workspace chain with the note "created via Create from <pack title> <version>"; `settings` (setting key → choice id, Pack settings above) are then recorded by `set_pack_settings` in the same transaction (`pack.settings_changed`). Owners and admins only; the owner must be a member; a level is never added this way (use Workspace admin › Packs).
- **Not yet reviewed.** Every sheet of a live set shows "Created by <name>" and, until the named owner presses Mark reviewed, "Generated from template, not yet reviewed" with the owner and the review date. `mark_bundle_reviewed(install)` accepts only the named owner, once, stores `reviewed_by` / `reviewed_at` and logs `bundle.reviewed`; the badge then reads "Reviewed by <name> on <date>".
- **Archive the whole set.** Owners and admins archive a set from any of its sheets ("Archive the whole set", an inline confirm): `archive_pack`, as above. Items and the activity log are kept.

- **Apps.** Create's App card (docs/05 §4 Create, docs/13) offers the apps of these sets: an app not set up yet is created as the set that carries it, through the same preview, `createBundle` and `create_bundle`.

A set is a pack install like any other: it shows under Workspace admin › Packs, upgrades as in Upgrades below (parts left out at create come back as additions there) and is created once per workspace (the wizard opens the existing one instead). The incident and internal audit starts ship as `start-incident` and `start-audit` 1.0.0 for this; a hosted catalogue needs them loaded (`scripts/packs-sql.ts`).

## Upgrades (P6)

A version is written once (change a pack, raise its version), and the catalogue keeps every version an install points at. A live install whose pack has a newer version **of the same major version** in the catalogue (`updateTarget`, `src/server/packs/upgrade.ts`) shows **Update available x → y** on Workspace admin › Packs (installed packs) and, for an adopted framework library (`framework-<key>`), on Workspace admin › Frameworks. Owners and admins open the update dialog. A new major version is a rebuild (Phase 2: a standard rebuilt as an add-on to the Core registers, `iso-27001` 1.3.0 → 2.0.0) and is never offered as an update: it is installed fresh once the old version is archived (owner decision: those workspaces are reset). A framework library's revisions keep the edition as the major, so they stay updates.

**The three-way diff** (`planPackUpgrade`, `src/engine/packs/upgrade.ts`, pure). Each object is matched by its stable ref through the install's `ref_map` and compared three ways:

- **base**: the installed version's manifest (read from the catalogue by the install's version; `pack_installs.manifest_hash` checked), planned as `install_pack` wrote it, with the plan's ids swapped for the install's;
- **mine**: the object as the workspace holds it now (read with the person's client; what they cannot read counts as removed by them and is left alone);
- **theirs**: the new manifest, planned the same way at the installed level (a level the new version dropped falls back to its lowest).

Per attribute: the pack did not change it → nothing; the client did not change it → the pack's change is applied; both changed it to different things → a **conflict**. Example items compare against what the install wrote (their `item.created` entry), so `$today` and `$in:N` values never read as changes; values merge field by field, so answers the pack never sets (status, owner, applicability) are never touched.

| Object | Compared | Rules |
|---|---|---|
| Folder | name | Removed from the pack: archived when nothing live is left in it |
| Sheet | name, description, item label | Removed: archived (restorable) only when it holds no items the client added and no example item the client changed; otherwise kept |
| Field | name, description, required, locked; settings key by key | **Add-only**: never a new type (a type change is kept and said), never removed (kept and said), options merged: the client's options stay in their order with their labels and colours, an option the client left as shipped takes the pack's new label and colour, new options are added, an option the client removed does not come back. New fields go after the sheet's last field |
| Group | name, colour | Removed: kept (it holds items) |
| View, form | name, settings | Removed: kept (views cannot be archived) |
| Example item, document | name, group, each value the pack sets | Removed: archived only when untouched since install; otherwise kept |
| Library requirement | the same | Rewords titles and the locked Purpose, Guidance, Audit questions and Typical evidence; new requirements are added with their requirement key; a requirement is never removed. Applicability, justification, status, owner and evidence are the client's |
| Automation | name, trigger, conditions, actions | The on/off state is the client's and never changes; removed from the pack: turned off |
| Approval workflows of a sheet | the sheet's `workflows` list as one value (an add-on's entries on it, ids in its namespace, are left out and kept) | Applied when the client left them as shipped; a conflict when both changed them (Keep mine / Take the pack's). Written after the rest in the same transaction (`update.workflows`, `apply_pack_upgrade`, which the app calls instead of `upgrade_pack`); approvals in progress keep the copy of the definition they started with. An add-on's workflows on a required pack's sheet: its own entries as one value (Extends) |
| Tab set of a sheet | `settings.tabs` and the tab that opens first, as one value (0044) | Applied when the client left them as shipped (`update.tabs`: tabs, the shipped default and the default view, views of that sheet only); a conflict when both changed them |
| Dashboard | name, widgets | Removed: archived when untouched, otherwise kept |

New objects are added as an install would add them (new sheets with their folder, fields, groups, views, forms, items and links; positions after what the workspace has; a taken ID prefix is renamed and said). Links are added only from an item or through a field the update adds; links the client made or removed stay as they are. Sub-items are not added to a sheet that already exists (said, with the automations that need them). Client-added objects (no provenance) are never touched.

**Dry run and apply.** `previewPackUpgrade` plans on the server and returns the preview: added, changed, archived or turned off, kept (with why), conflicts and warnings, and the counts. The dialog shows each conflict with **Keep mine** (the default) or **Take the pack's**. `upgradePack` plans again from the catalogue and the workspace as they are now with those choices (the browser sends only the install, the new version's hash and the choices; a changed catalogue is refused) and calls `upgrade_pack(install, plan)` (0035): owners and admins, the plan for the version and hash installed now, only the install's own rows updated (only the columns the plan names; an option removed or a sheet with client items archived is refused), added rows with the install's provenance, new library items stamped with their requirement key (checked against the catalogue and the item's Ref), every item change logged on the item's chain (note "Pack update"), structure changes by the schema audit, and `pack.upgraded` on the workspace chain with the old and new version, the counts and the summary of conflicts. The install moves to the new version and hash and its ref map grows. One transaction: any failure leaves the workspace as it was. The result toast says how many objects were added, changed and archived and how many conflicts were kept.

## Pack quality bar

Owner-approved (board, Nov 2026). Every native pack in `templates/packs` meets it; `packQualityProblems` (`src/lib/packs/quality.ts`) checks it and `src/lib/packs/quality.test.ts` runs it over every pack file (framework libraries and wizard starts are not native packs). Packs not upgraded yet are listed in `src/lib/packs/quality-allowlist.json`; the test fails while a listed pack passes, so a rewrite that makes a pack pass removes its key from the list in the same commit. Since Core registers 1.1.0 the list is empty: every native pack meets the bar. `pnpm exec tsx scripts/pack-quality.ts [key …]` prints the problems.

**Keys for pack authors**

| Key | Where | Meaning |
|---|---|---|
| `kind` | `sheets[]` | What the sheet is for: `register` (things kept up to date: risks, documents, suppliers), `actions` (work with an owner and a due date: CAPA, tasks), `log` (dated events: incidents, meetings), `library` (reference items; an `isLibrary` sheet is one), `plan` (dated work over time: an audit programme) |
| `personalData` | `sheets[]` | `true`: the sheet holds personal data. It installs **restricted** (docs/02 §16: owners always, admins and the person installing listed), whatever `restricted` says (`restricted: false` is refused), and at least one of its fields must say `config.personalData: true` |
| `startInTestMode` | `automations[]`, `extends[].automations[]` | `true` / `false`: installed in test mode or live (docs/04 §14). Not set: test mode when the automation notifies anyone or sends anything out |
| `advanced`, `description` | `automations[]`, `extends[].automations[]` | An advanced automation (escalation, cascade, gate, recurring work, SLA), with what it does and why in plain words (≤ 400 characters; required when `advanced`) |
| `headline` | `dashboards[]` | The pack's headline dashboard |
| `formsNotApplicable` | the manifest | Why the pack ships no intake forms (a pure library or add-on), in a sentence |

**Safety at install** (every pack, whatever the bar):

- **Quiet first week:** automations that notify or send out install in test mode (above; docs/04 §14). The install preview says "(test mode: logs what it would do until you turn it on)"; the Create wizard says "Created in test mode".
- **Outbound off:** an automation with a `webhook` or `email` action installs **off** unless the person installing opts in (`installPack` `allowOutbound: true`; the Create wizard always installs them off and flags them). They turn it on after checking where it sends.
- **Personal data restricted:** `personalData` sheets install restricted. Dashboard widgets read through the person's own access: a widget on a sheet they cannot open shows "No access" and nothing of its data (`computeDashboard` with the person's client and `sheet_levels`).

**The rules** (rule id · what passes):

| Rule | Passes when |
|---|---|
| `sheet-kind` | Every sheet has a `kind` (`isLibrary` counts as `library`) |
| `tabs` | At most **4** visible tabs per sheet. A sheet without `tabs` shows all five built-in views, so every sheet needs a tab set (hide the rest) |
| `views` | Per kind, among the visible tabs: **register** → Table, a Board by status (a saved kanban view whose `labelFieldKey` is the status field; any Board when the sheet has no status field), and a Calendar when it has a review or expiry date field (a date field whose key or name says review, expiry, valid or renew). **actions** → Table, a Board, a due date field (key or name says due or deadline) and a Calendar on it (a saved calendar view whose `dateFieldKey` is that field, or the built-in Calendar). **log** → Table and Calendar. **library** → Table. **plan** → Table and a Timeline once that view type exists, a Calendar until then |
| `advanced-automations` | At least **4** automations (own and in `extends`) with `advanced: true` and a `description` |
| `headline-dashboard` | Exactly **one** dashboard with `headline: true` |
| `intake-forms` | At least **2** forms (own sheets and `extends`), or `formsNotApplicable` with the reason |
| `approvals` | An approval workflow (`sheets[].workflows`, docs/04 §13) on every documents register (document approval), every `register` sheet whose ref or name says risk (risk acceptance) and every `register` or `actions` sheet whose ref or name says nonconformity, corrective, CAPA or is `nc` (CAPA closure) |
| `starter-size` | The lowest level (the whole pack when it has no levels) installs at most **5** sheets and **1** dashboard |
| `standard-text` | Never a standard's text (docs/12 Licensing): in a pack building on an ISO framework, example items of sheets other than documents registers and libraries are named "Example: …"; no string anywhere says "the organization shall" |

## Frameworks

A framework's requirement library is a generated pack (docs/12): `frameworkToPack` (`src/engine/frameworks/pack.ts`) turns a framework file into a manifest with one library sheet (key `framework-<key>`, or `framework-<key>-<version>` for a later edition so both editions install side by side; version `<edition>.<revision>.0`). An update offers a new revision of the same edition only; a new edition is adopted and moved to (docs/12 Moving to a new edition). The sheet carries `framework: { key, version, refFieldKey }` and each item a `requirementRef` (`<framework>@<version>#<ref>`). The seed writes these packs with the others and then the requirement catalogue (`syncFrameworks`). They are not listed under Packs and `previewPack` / `installPack` refuse them: a framework is adopted from Workspace admin › Frameworks, through `adopt_framework`, which calls `install_pack` and stamps the requirement keys in the same transaction. An adopted library is archived like any pack (Installed packs › Archive).
