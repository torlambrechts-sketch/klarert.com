# 11 · Packs

A **pack** is an installable bundle of the core as data (CLAUDE.md: data, not code): folders, sheets with fields, groups, views, forms, tab sets and column groups, sub-items, example items, documents and library items, links, automations and dashboards. Installing a pack writes ordinary rows; nothing in the app knows a pack's content. Milestones P1–P7 in docs/06; tables and RPCs in docs/02 §15.

## Where packs come from

| Source | Becomes |
|---|---|
| `templates/packs/*.json` | Native pack files (the manifest below), e.g. `supplier-management.json` |
| `templates/first-sheet.json` | Wrapped by `templateToPack` (`src/lib/packs/wrap.ts`): key = the template id, refs made from names |
| Wizard starts (`templates/starts.json`) listed in `START_PACKS` | Wrapped by `startToPack`: one sheet, key `start-<id>` (CAPA, Documents and policies). A start's `pack` adds the pack's version, automations and dashboards (the wizard ignores it) |
| `templates/apps/*.json` | An app for the pack it `requires` (docs/13), added to that pack's `apps` by `withApps` |

`repoPacks()` (`src/lib/packs/catalogue.ts`) parses all of them. The seed (`pnpm seed`, `scripts/seed.ts`) writes them into the global `packs` table; the app reads only that table. A version is written once: change a pack, raise its version. In a hosted environment run the seed's catalogue step (or an equivalent service-role job) after a deploy that adds a pack version.

The wizard keeps creating a start's sheet its own way (editors may use it, the person picks name, prefix and columns); the same starts are also offered as packs to owners and admins. The template importer (`src/server/templates/importer.ts`, used by the seeds) installs through `install_pack`.

For a hosted project, `pnpm exec tsx scripts/packs-sql.ts > packs-catalogue.sql` writes the repository's packs as idempotent inserts (`on conflict do nothing`); run it as the database owner after the migrations and after `scripts/frameworks-sql.ts`.

## The manifest

Validated by `packManifestSchema` (`src/lib/packs/manifest.ts`), which extends the sheet template schema and then runs the template's own checks on every sheet.

| Key | Meaning |
|---|---|
| `key` | `^[a-z0-9][a-z0-9-]{0,79}$`, the pack's identity |
| `version` | Semver `1.2.3` |
| `title`, `description` | Shown in Workspace admin › Packs |
| `requires` | `[{ pack, range }]`; ranges `1.2.3`, `^1.2.0`, `~1.2.0`, `>=1.2.0`, `*`. Installing the pack installs a required pack first when it is missing (at the level the pack needs), or raises it to that level; a version out of range blocks |
| `people` | Example people by `ref` and `email`; values `$person:<ref>` match the workspace's members by email. Missing people are left out (a warning, never a blocker) |
| `folders` | `[{ ref, name, restricted? }]`. An active folder with the same name is used; otherwise the pack makes one. `restricted: true` (P2) makes a new folder restricted: the installer is listed as an editor (owners always see it) |
| `sheets` | A template sheet (docs/07 Part B: `ref`, `name`, `itemLabel`, `idPrefix`, `groups`, `fields`, `views`, `forms`, `tabs`, `defaultView`, `columnGroups`, `subitems`, `retention`) plus `folder` (a folder ref), `isLibrary`, `register: "documents"`, `restricted` (P2: created restricted, the installer listed as an editor), `uniqueLinks` (two link field keys: one live item per pair of targets, `sheets.settings.uniqueLinkPair`, docs/02) and `items` |
| `sheets[].fields[].config.targetSheetRef` | A link: a sheet ref of this pack, or `<pack key>:<sheet ref>` of a pack in `requires`, resolved at install through that pack's live install (both ways when that sheet's `extends` adds the inverse field) |
| `sheets[].retention` | `{ personalNames?, rules: [...] }`: retention rules (docs/02 §18) stored in `sheets.settings.retention`, groups named by ref (`groups: ["closed"]`, resolved to ids). Checked: unique ids, the date field exists, `fieldKeys` are fields marked personal data. Periods a pack ships are suggestions: say so in the rule's `note` |
| `sheets[].fields[].config.personalData` | `true`: the field holds personal data (masked in the log, erasable under retention, docs/02 §18) |
| `sheets[].workflows` | Approval workflows (docs/04 §13) stored in `sheets.settings.workflows`: steps, approvers by a people field of the sheet, a job role or a team **by name** (`{ "kind": "jobRole", "roleName": "Top management" }`; people and ids belong to a workspace and are refused), modes, SLAs, rejection targets, required fields, the step field and the status field with their option ids. Checked against the sheet's fields (`workflowProblems`). A role or team the workspace lacks is not an error: submitting names it ("Give a member the job title Top management") |
| `sheets[].items` | `[{ ref, group, name, values, links: { <link field key>: [<item ref>] }, requirements? }]`: example items, documents of a register, library items. Links name items by ref, never by name. Tokens `$today`, `$in:N`, `$option:<label>`, `$person:<ref>` |
| `sheets[].items[].requirements` | `{ <requirement or control link field key>: ["iso-27001@2022#A.6.3", …] }`: example links into the library of a framework in `frameworks` (requirement keys, docs/12), resolved at install (Frameworks below) |
| `automations` | Template automations plus a `ref`. `sheetRef`, `groupRef` and a form's `ref` resolve to ids; `jobRole:<name>` / `team:<name>` recipients the workspace lacks are left out and said; an automation that then has nobody to tell is installed off |
| `automations[].subitems` | `true`: the automation belongs to the sheet's sub-items (docs/02 §12), i.e. the hidden child sheet of `sheet` (ref map `sheet:<ref>.subitems`). Its trigger and conditions name the sub-items' field keys; the sheet must have `subitems`, and a form trigger is not allowed. Date triggers fire per sub-item; `{sheet}` in a message is "<sheet> · <sub-items label>" |
| `dashboards` | `[{ ref, name, widgets: [{ ref, type, title, sheetRef?, library?, fieldKey?, conditions?, days? }] }]`, checked against the widget registry. `library: "<framework>@<version>"` (one of `frameworks`) reads the workspace's library sheet of that framework instead of a sheet of the pack |
| `levels` | Optional, 2–5, lowest first: `[{ key, name, description }]` (Levels below) |
| `level` on folders, sheets, forms, automations, dashboards | The lowest level that installs the object; none = every level |
| `frameworks` | `[{ key, version, optional? }]`: framework libraries the pack builds on, adopted at install when missing (Frameworks below). `optional: true` is soft: never adopted for you; example links into it are written only where the workspace has adopted it, and widgets and setup steps may not read it |
| `setup` | `{ title, description, steps }`: the guided setup checklist (Setup below) |
| `apps` | Apps over the pack's sheets, forms and dashboards (docs/13), checked against the pack's refs |
| `system` | `true`: a system pack (the Core registers): its sheets are shared registers ("System board", `sheets.settings.system`) and its fields system columns (`fields.system`) |
| `folders[].domain` | A domain folder of shared registers (`management`, `risk` …): listed under Registers in the side menu in the manifest's order, hidden while it has no live sheet, never reusing a folder of the same name |
| `sheets[].folder` | Also `<pack>:<folder ref>`: a folder of a pack in `requires` (an add-on's sheet in a Core domain) |
| `standard` | `{ id, label, color? }`: the standard an add-on stands for. Its option is added to the Standards field of every sheet it extends, with a saved Table view "<label> view" filtering Standards has any of it. The id is in the pack's namespace |
| `extends` | `[{ pack, sheet, fields?, groups?, views?, forms?, items?, automations?, options? }]`: what the pack adds to a sheet of a pack in `requires` (Extends below) |

ID prefixes are unique inside a pack. When the workspace already uses one, the planner renames it with a number (`SUP-` → `SUP2-`, cutting the stem to stay within 6 characters) and the preview says so.

## Install

1. **Preview** (`previewPack`, owners and admins): the server reads the manifest from the catalogue, takes a snapshot of the workspace (prefixes, folders, installs, members with emails, job roles, teams, last positions) and runs the pure planner `planPackInstall` (`src/engine/packs/plan.ts`). The planner reuses the template planner (`src/engine/templates/plan.ts`) for everything sheet-level and returns operations per object (`create`, `reuse`, `skip`, `conflict`), the preview (counts, folders, sheets, links, renamed prefixes, automation sentences, forms, dashboards, warnings, conflicts) and the rows.
2. **States:** `ready`; `installed` (the same version is installed: every operation is `skip`); `blocked` (another version is installed, a requirement is missing or at the wrong version, a link into another pack, a widget that does not fit, a document that would start approved, a value the template planner refuses).
3. **Install** (`installPack`): plans again from the catalogue and the workspace as they are now (the browser sends only the key and the hash it previewed; a changed manifest is refused) and calls `install_pack`, which writes everything with provenance and the ref map in one transaction and logs `pack.installed`.

## Levels

A pack may offer levels (`levels`, lowest first, e.g. Starter and Full), chosen in the install dialog, which shows what each level creates and what it adds to the one before (`levelSummaries`). Every folder, sheet, form, automation and dashboard may name the lowest level that installs it; without one it installs at every level. `manifestAtLevel` (`src/engine/packs/levels.ts`) is the manifest as installed at a level.

- The manifest is checked so that nothing needs a higher level than its own: a sheet's folder and link targets, an automation's sheets (its own and `sheetRef` in actions), a dashboard's widgets, a form after its sheet. A two-way link joins sheets of one level only (a higher level never adds a field to a sheet already installed), so links from a higher level to a lower one are one way.
- `pack_installs.level` (0032) keeps the level installed. Installing a higher level of the same version later is not a new install: the planner plans the level whole, leaves out every row whose ref is already in the install's `ref_map` and points the new rows at the existing ids (`extend_install` in the plan). `install_pack` then adds the rows to the same install, refuses a level already installed or a ref the install already has, merges the ref map and logs `pack.extended` with what the level added. Picking a level at or below the installed one is `installed` (nothing to do).
- Workspace admin › Packs shows the installed level and an "Add Full" button that opens the dialog on the next level.

## Frameworks a pack builds on

`frameworks: [{ key, version, optional? }]` names framework libraries (docs/12) the pack needs. An `optional` one is never adopted by the install (the preview says "Links its items to the … library you have adopted" when it is there); its example links are written only where it is adopted, like any key the library lacks. A new pack version may name a newer edition; an update then warns that the edition is not adopted and leaves the old library alone (ISO 9001 1.1.0 below). The preview says which are not adopted yet ("Adopts the ISO/IEC 27001:2022 requirement library first"); `installPack` adopts them first with `adopt_framework` (each its own transaction, no controls sheet) and then plans the pack again so it finds the library. The pack's sheets link to library items through `requirement` fields with no target sheet (any library); its widgets read the library with `library`.

Example items may link into a required library by requirement key: `"requirements": { "controls": ["iso-27001@2022#A.6.3", "iso-27001@2022#A.8.7"] }` on a risk (the field a `requirement` or `controllink` field of the sheet; the key's framework one of `frameworks`, checked by the manifest schema). `planInstall` reads the adopted library's live items with those `requirement_ref`s (`PackSnapshot.requirementItems`) and the planner writes the links with the install, so the requirement (and the SoA) shows the linked risks at once. Before the library is adopted (the preview) the links are left for the install, which adopts first and plans again; a key the library does not have is left out with a warning, never a blocker. `install_pack` (0033) accepts a link whose target is outside the plan only through a requirement or control link field and only to a live item of a live library sheet of the same workspace. A higher level never writes such a link again (its item and field are already installed).

## Setup

`setup` is a checklist shown after install on Workspace admin › Packs (all steps) and as a dismissible card on Home (the next step; dismissing is kept per browser). Each step has a `ref`, a title, a short own-words body, a `target` (a pack sheet by `sheetRef` or a required library by `library`, optionally a saved view or a form of that sheet by name: the link opens it, a form in the Forms tab) and `rules`. A step may reword itself at a level (`levels: { starter: { title, body, target, rules } }`), e.g. "List your processes" when Starter has no asset register.

Progress is computed from data by the pure `setupProgress` (`src/engine/packs/setup.ts`): for each rule, of the items matching `where` (all items when empty), the share that also match `all`, counted against at least `min` items (`matched / max(counted, min)`); conditions use the condition operators by field key. A step's progress is the average of its rules; the checklist's percent is the average of its steps (100 only when every step is done). Sheets the person cannot read count as not started and link nowhere. The checklist is checked at every level: each step names sheets, fields and views that level installs.

## The Supplier management pack

`templates/packs/supplier-management.json` (key `supplier-management`, version 1.1.0, folder Suppliers): Supplier register, Supplier reviews, Supplier requirements (the library), Supplier documents (a documents register) and, from 1.1.0, Supplier requirement checks.

**Board decision (Nov 2026, owner-approved): per-supplier requirement sets.** The requirement library is the master list and says which suppliers each requirement applies to; every supplier gets one check per requirement that applies, kept in step by an automation, never deleted, with the answer, evidence and expiry on the check. Links to ISO/IEC 27001, ISO 9001 and the GDPR are soft: the pack links only to libraries the workspace has adopted and never adopts one for you.

- **Library (Supplier requirements):** 13 requirements in our own words (signed contract with security terms, confidentiality agreement, DPA (Art. 28), sub-processor list, transfer mechanism, breach notice within 24 hours, right to audit, return or deletion at exit, ISO/IEC 27001 certificate or SOC 2 report, business continuity, liability insurance, ISO 9001 certificate, delivery performance), each with **Applies to** (Every supplier, By category and criticality, Suppliers that process personal data (Art. 28), Only when added by hand), **Applies to categories** (the supplier categories; empty = all), **Applies from criticality** (minimum; empty = all), **Framework requirements** (27001 A.5.19–A.5.22, 9001 8.4, GDPR Art. 28 and 46 where adopted), **Version** (raised when the guidance changes) and the checks.
- **Supplier register:** **Processes personal data** (the Art. 28 set), **Extra requirements** (the 1.0.0 Requirements field, renamed: requirements added by hand), **Requirement checks** (two-way link, shown as a checklist in the panel with Evidence and Evidence expires; empty state "Choose a category and criticality and we will add the requirements for this supplier."), roll-ups **Requirements met** ("7 of 9", `doneOf`), **% met**, **Worst check** and **Expired evidence** (`countExpired` on the expiry date), all leaving out Not applicable and No longer applies, and the **Sync requirements** button. A "Requirements" view sorts by % met.
- **Supplier requirement checks:** Supplier and Requirement (two-way links; `uniqueLinks`, so the database keeps one check per pair), **Status** Not checked (default, neutral), Met (done), Not met (needs action), Not applicable, No longer applies; Evidence (files, 365 days), Evidence documents (link to Supplier documents), Evidence expires, Checked by, Checked on, Why not applicable and Not applicable approved by (shown and required when Not applicable: a status rule blocks without both), Source (Rule, Added manually (default), Art. 28), Requirement wording and Library version (lookups), Wording when checked and Version when checked (locked fields, frozen by an automation when the status moves off Not checked), Sync note, Supplier owner. Views: All checks (cross-supplier, filter by supplier or requirement), Not met, Expired evidence, Not checked, By status. Access follows the supplier register: same folder, inheriting its access.
- **Automations (16):** review due and review failed (1.0.0); sync the supplier's checks when a supplier is added, its category, criticality, Processes personal data or Extra requirements change, or Sync requirements is clicked (owner told when new checks lower % met); re-sync every supplier when a requirement is added or its Applies to, categories or criticality change (batched, 200 a run); raise the requirement's version when its guidance changes; when a check is answered, record who, when, the wording and the version; tell the supplier owner when a check is not met and 30 days before Met evidence expires. All use `sync_requirement_checks` (docs/04) or core actions.
- **Example checks** for Northwind Cloud Hosting (High, IT and cloud, processes personal data): contract and DPA met, the 27001 certificate met with expired evidence, the transfer mechanism not met. Sync requirements adds the other 7 ("Added 7, flagged 0"). Install runs no automations, so the other example supplier gets its checks on the first sync.
- **1.0.0 → 1.1.0 (P6):** the upgrade adds the checks sheet (in the install's Suppliers folder), the new fields on the register and the library (add-only; the two-way link between the register and the new sheet is wired both ways), the 10 new library requirements, the example checks and the new automations; it rewords the three 1.0.0 requirements and the renamed field where the workspace left them as shipped. Requirements a workspace added itself have no Applies-to rule, so they apply only when added by hand. Covered by `src/lib/packs/supplier-management.test.ts` against the 1.0.0 manifest (`src/lib/packs/fixtures/`).
- Hosted: apply migration 0038 and load the new version with `scripts/packs-sql.ts`.

## The ISO/IEC 27001:2022 pack

`templates/packs/iso-27001.json` (key `iso-27001`, version 1.1.0): Starter has Scope and context, Risk register (likelihood and impact 1–5, inherent and residual scores as formulas, treatment option, Annex A controls from the library, review date), Risk treatment plan, ISMS documents (a documents register with the documented information an ISMS keeps) and Nonconformities and CAPA (actions as sub-items, the close gate); Full adds Asset register, Internal audit programme, Audit findings, Management review (inputs as checkboxes), Security incidents and Training and awareness. Nine automations (risk review due, residual score above 12, overdue nonconformity, overdue corrective action on the CAPA actions (sub-items, tells the action's owner), overdue treatment action, document review due, and in Full: a nonconformity finding or a closed incident that needs a root cause raises a linked nonconformity, training due), the "ISMS overview" dashboard (risks by level, by status, treatment progress, Annex A implementation from the library, open nonconformities, documents due for review) and an 8-step setup. Example items start with "Example:"; no text of the standard is shipped (docs/12 Licensing).

- **Annex A links.** The example risks link to Annex A controls of the adopted library (phishing → A.6.3, A.8.7; lost laptop → A.8.1, A.7.9; supplier outage → A.5.19, A.5.30) and the example treatments to the control they put in place (multi-factor sign-in → A.8.5, disk encryption → A.8.24), so the requirements show linked risks straight after install.
- **Report a security incident** (Full, on Security incidents): what happened (one line and the detail), when it was noticed, systems and data affected, a severity guess and the reporter's name and email; answers go to Open with the status New. It installs as an **internal** draft (signed-in members of the workspace), with a privacy notice to review. To take reports from people without an account (staff without a seat, contractors), an owner or admin switches it to public in the form's settings and opens it: the reporter's name and email are then the only way to reach them, and the notice must be reviewed first (docs/05 §3.3). The sheet shows its Forms tab and the setup step "Make incidents easy to report" opens the form (Starter: "Record incidents" as nonconformities with the source Incident).
- **1.0.0 → 1.1.0.** A workspace on 1.0.0 keeps it until an owner or admin updates it (Upgrades below); new installs get the newest version. Hosted catalogues need the new version loaded (`scripts/packs-sql.ts`) after migration 0033.
- **1.2.0 (P7).** Adds the internal form "Report a problem" on Nonconformities and CAPA (Starter), the "Nonconformities overview" dashboard and the ISMS CAPA app (docs/13).
- **1.3.0 (approval workflows).** ISMS documents gets the read-only **Approval step** field and the **Document approval** workflow: Document ID and Owner filled before submitting; step 1 Owner review (the document's Owner, 5 days, a rejection back to draft); step 2 Management approval (everyone with the job title Top management, 10 days, a rejection back to Owner review); Status set to In review on submit, Approved on approval (the register's rules apply: the approver's comment is the version note, a current file is needed, never the author) and Draft on rejection; the document is locked when approved. The submitter never approves their own document. Hosted catalogues need 1.3.0 loaded (`scripts/packs-sql.ts`) after migration 0040; installs on 1.2.0 see the update.

## The ISO 9001 pack

`templates/packs/iso-9001.json` (key `iso-9001`, title "ISO 9001 QMS", version 1.1.0, folder Quality management) builds on the `iso-9001@2026` library (1.0.0: `iso-9001@2015`), adopted at install when missing. Written as a lead auditor would want to find it: every sheet answers a clause, every record an auditor samples has a field for it.

- **Starter (7 sheets):** Context and interested parties (issues, parties and what they need, the scope statement with the requirements that do not apply and why), Quality policy and objectives (policy commitments; objectives with how each is measured, a target, the latest result, "Lower is better" and the formula Against target: Met or Not met, the plan, due and review dates), Processes (owner, inputs, outputs, measures, resources, linked risks and objectives), Risks and opportunities (likelihood and impact 1–5, score and level as formulas, the action and whether it worked, a close gate), Quality documents (a documents register with the documented information a QMS keeps: policy, scope, process descriptions, document control, and the records: competence, calibration, internal audit, management review, approved providers, nonconformities, release), Nonconformities and corrective action (source, the product affected, what happened to the output (corrected, held, returned, concession, scrapped), correction, root cause, corrective action, effectiveness check; actions as sub-items that block closing) and Customer feedback and complaints (complaints, praise, suggestions and survey results; the answer is required to close; "Needs corrective action" raises a linked nonconformity).
- **Full adds (8 sheets):** External providers (criteria, evaluation score and date, next evaluation, certificates as evidence, linked nonconformities; approving needs the criteria and both dates), Competence and training (competence needed, how, evidence, was it effective), Measuring equipment (ID, range and accuracy, interval, last and next calibration, traceability, certificates, what was done when found out of tolerance), Internal audit programme (processes and clauses in scope, lead auditor) with Audit findings (nonconformity major or minor, observation, opportunity), Management review (the twelve inputs as checkboxes, decisions and outputs), Design and development (optional: leave it empty or archive it and say why in the scope) and Release records.
- **Automations (8):** objective review in 14 days, document review in 30 days, a complaint that needs corrective action raises a linked nonconformity, nonconformity overdue, corrective action (sub-item) overdue to the action's owner; in Full: calibration due in 30 days, supplier re-evaluation in 30 days, an audit finding of type Nonconformity raises a linked nonconformity.
- **Forms:** "Report a complaint" (Customer feedback and complaints, Starter: customer, contact, what they said, product or order, when, channel, severity, who logged it; prefilled as a New complaint) and "Report a nonconformity" (Starter: what is wrong, what is affected, where it came from, what was done so far, severity, name). Both install as **internal** drafts with a privacy notice to review; switch to public only after reviewing it (as for the 27001 incident form).
- **Dashboard "QMS overview" (10 widgets):** objectives by status, open complaints, feedback by kind, open nonconformities, nonconformities by source and past their due date, risks and opportunities by status, processes by status, documents due for review, and the 9001 requirements by implementation (from the library).
- **Setup (8 steps):** context and scope (with every requirement marked applicable or not), policy and objectives, processes and their risks, documents, complaints (opens the form), external providers, internal audit, management review. At Starter the last three point at the approved records in Quality documents (`QMS-REC-SUP`, `QMS-REC-03`, `QMS-REC-MR`).
- **Library links:** example items link to the clauses they show: context → 4.1, 4.2, 4.3; policy → 5.2; objectives → 6.2 (and 9.1.2); processes → 4.4, 8.2, 8.4, 8.5; risks → 6.1; complaints → 9.1.2, 8.7; nonconformity → 10.2, 8.7; supplier → 8.4; competence → 7.2, 7.3; equipment → 7.1.5; audit → 8.2, 8.4, 8.5; finding → 8.4; design → 8.3; release → 8.6; each document to the clause it meets. Example items start with "Example:"; no text of the standard is shipped (docs/12 Licensing).
- **Management review inputs:** `REVIEW_PACK_SOURCES` maps the pack's review, context, nonconformity, risk, audit, finding, competence and customer feedback sheets; "Add to Management review" ticks the 9001 sheet's own input checkboxes. Customer feedback (source `feedback`, date Received on, grouped by Kind) feeds "Needs and feedback of interested parties": what was received in the period by kind and what is still open, and overdue feedback is listed under opportunities.
- **Prefixes** (`QCX-`, `QOB-`, `PRC-`, `QRO-`, `QMD-`, `QNC-`, `CFB-`, `EXP-`, `CMP-`, `MME-`, `QIA-`, `QAF-`, `QMR-`, `DEV-`, `REL-`) do not clash with the 27001 pack, so both install side by side.
- Hosted catalogues need the pack loaded (`scripts/packs-sql.ts`) and the 9001 library at revision 4 (`scripts/frameworks-sql.ts`). No migration.
- **1.0.0 → 1.1.0 (ISO 9001:2026).** 1.1.0 builds on the 2026 edition: the example items, the dashboard's library widget and the setup step name `iso-9001@2026` clauses (the same clause numbers; risks still link to 6.1, now the parent of 6.1.1 to 6.1.3). New installs adopt ISO 9001:2026. A workspace on 1.0.0 keeps its ISO 9001:2015 library when it updates: an update never adopts a framework and never moves a library. ## Audit outputs (P5)

Exports for an auditor or a management review, made from the workspace as it is now. Insights › **Audit outputs** (`/[org]/audit`) has all three; every member may use them, auditors too (exports change nothing). Shortcuts: **Export SoA** on a library sheet's header and on Workspace admin › Frameworks (with the audit pack dialog), and "Compile the review inputs" on the setup step whose sheet is the pack's management review sheet.

- **Statement of applicability** (`/[org]/audit/soa/[sheetId]`, a server-rendered page that prints to PDF from the browser; the shell is hidden in print; CSV by a form POST to `./csv`). Rows: the library's SoA view (the view the framework file names, with its filters as the workspace keeps them; "Show every requirement" drops them). Columns Ref, Title, Applicable, Justification, Implementation status, Owner, Evidence (file names with a link to the item), Linked controls and risks (items linked either way, not other libraries' requirements), Last reviewed. Header: workspace, framework, scope, the framework's licence note, generated at and by. Only the shipped titles; never a standard's text. Pure: `buildSoa`, `soaCsv`, `soaHtml` (`src/engine/audit/soa.ts`).
- **Audit pack** (POST `/[org]/audit/pack`, `buildAuditPack`): scope the whole workspace, a folder or a pack install, a period, and optionally the evidence files. The zip holds `README.txt` (what is in it, what was left out, the method), `soa/<framework>.csv` and `.html` for each library in scope (for a pack: also the libraries it builds on), `registers/<sheet>.csv` for every sheet in scope (sub-item sheets too), `evidence/index.csv` (file, sheet, item, field, uploaded by and at, valid until, size, SHA-256 as checked at upload, whether the file is in the zip) and `evidence/files/<item>/<file>` when asked: each file up to 10 MB and 100 MB in all (`AUDIT_FILE_LIMITS`, smallest first), each through `download_file` (blocked files never, each counts as a download), `activity/log.csv` (the entries of the scope's sheets and items whose day in the workspace time zone is in the period; restricted values read "Restricted") and `activity/chains.csv` with `method.txt`: `verify_activity_chain` on every chain in scope (each live item, each sheet, and every chain with an entry in the period), ok, broken (with the first bad entry) or not checked. The whole chain is checked, not only the period. The zip is built in memory with `fflate` (no zip library was in the dependencies; it is small and has none of its own); the file cap bounds it.
- **Management review inputs** (`/[org]/audit/review?from&to`, `managementReviewInputs`): the pure `compileManagementReview` (`src/engine/audit/management-review.ts`) words eight inputs for the period from rows the server projects with the field registry: actions from earlier reviews (reviews dated before the period, nonconformities and treatment actions still open from before it), changes in issues and in interested parties (context items added or changed, and customer feedback received and open), nonconformities (raised, closed, open, overdue), monitoring (each library's coverage as Frameworks shows it, incidents in neutral words so a security, quality or privacy incident sheet can feed it, training), audits and findings, risks (open by level, past review, treatment progress) and opportunities (overdue items, closed nonconformities). Where the inputs come from is data: `REVIEW_PACK_SOURCES` (`src/lib/packs/management-review.ts`) names the ISO 27001 and ISO 9001 packs' sheets, date and level fields, group refs and review checkboxes by pack ref. With a pack's Management review sheet, editors can **Add to Management review**: `createItem` (the inputs that have data ticked) and the report posted as the item's first update (`postUpdate`), so validation, the log and automations run as usual. "Closed in the period" is a done item last changed in the period.

**Access.** Everything is read with the person's own client: restricted sheets they cannot open are left out (the read me counts them without naming them), restricted fields they are not listed on are dropped from registers and read "Restricted" in the SoA and the log, and their files are not listed.

**Logged.** Every export writes `audit.exported` on the workspace chain through `log_audit_export(org, kind, scope)` (0034): kind `soa.print`, `soa.csv`, `audit_pack`, `management_review` or `management_review.item`, and the scope (framework, sheet, folder or install, period, counts, chains ok and broken). Members only (an auditor's access ends at its end date); the scope is a flat object of known keys with scalar values. Downloads are POST only and refused from another site.

## Archive

`archivePack` → `archive_pack`: automations off, sheets archived (restorable one by one from Workspace admin › Archived), folders archived when nothing else is in them, dashboards archived, the install marked archived, `pack.archived` logged. Items, links and the activity log are never deleted. An archived pack can be installed again (its prefixes are then renamed, as the archived sheets keep theirs).

A pack another live install builds on (names it in `requires`) is not archived: "Archive ISO 14001 … first: it builds on this pack." An add-on's archive also takes back what it added to other packs' sheets (Extends below) and nothing else.

## Core registers

**Owner decision (Nov 2026, board unanimous, option B).** One set of shared registers, the **Core registers** (`templates/packs/core.json`, key `core`, version 1.0.0, `system: true`), that every standard builds on as an **add-on**: a risk, an incident or a document is recorded once and counts for every standard that uses it. Phase 1 is the platform and the Core pack; rewriting the standard packs as add-ons is Phase 2 (docs/06).

- **Domains** (folders with a `domain`, in this order): Management system (Documents and policies, Objectives and KPIs, Legal register, Competence and training, Internal audits, Management reviews), Risk and controls (Risk register, Risk categories, Controls library, Assets), Operations (Incidents, Nonconformities and CAPA, Actions), Privacy and security and Suppliers (no Core sheets: add-ons fill them). A domain without live sheets is hidden in the menu.
- **Levels:** Starter (Documents and policies, Objectives and KPIs, Risk register, Risk categories, Incidents, Nonconformities and CAPA, Actions) and Full (adds Legal register, Competence and training, Internal audits, Management reviews, Controls library, Assets). An add-on gets the lowest level that has every sheet and folder it uses (`neededLevel`); Core alone installs at the level chosen.
- **Risk methodology as data:** one methodology per risk category. Risk categories is a register (likelihood scale and impact scale in words, appetite = the highest score accepted without treatment); each risk links to its category, the Appetite lookup reads it and "Against appetite" compares the score (likelihood × impact). Core ships "General"; add-ons add their own categories (the 14001 add-on: Environmental, appetite 6).
- **Every sheet** has a **Standards** multi-select ("All standards"; add-ons add theirs; never used for access), a Table view with every row first (it backs the Table tab, so an add-on's view stays a chip), a Board by its status field and a Calendar on its due or review date. Core has no timeline view type yet, so no Timeline. Seven automations (document review in 30 days, objective and risk review in 14 days, nonconformity and action overdue; in Full legal evaluation in 30 days and training expiry in 60 days) and the dashboard "Management system overview" (open and overdue nonconformities, risks, objectives and incidents by status, documents due for review, overdue actions).
- **System board and system columns:** Core's sheets show "System board · installed by Core registers 1.0.0" and "Used by <standards>" (docs/05 §3); their columns, and the columns add-ons add to them, are system columns: hidden and renamed, never deleted, retyped or re-keyed (`fields.system`, docs/02).
- Own words throughout, no text of any standard (docs/12 Licensing); example items start with "Example:".

**The ISO 14001 demonstration add-on** (`templates/packs/iso-14001.json`, key `iso-14001`, 1.0.0, title "ISO 14001 environment (add-on)") proves the mechanism and is replaced by the Phase 2 pack: `requires` core ^1.0.0, `standard` ISO 14001; extends Risk categories (the Environmental category), Risk register (an "Environmental aspect" column linked both ways to its own sheet, an example spill risk in the Environmental category tagged ISO 14001, an automation when an ISO 14001 risk scores 12 or more), Incidents (the Environmental incident type, merged into the Type options), Objectives and KPIs (tag and view only); its own sheet Environmental aspects sits in Core's Operations domain (`folder: "core:operations"`) and links to objectives.

## Extends

`extends: [{ pack, sheet, fields?, groups?, views?, forms?, items?, automations?, options? }]` adds to a sheet of a pack in `requires` (`src/engine/packs/extend.ts`).

- **Rules (manifest checks, `extendsProblems`):** `pack` is in `requires` and is not the pack itself; one entry per sheet; field keys, group, item and form refs and option ids are in the pack's **namespace** (`namespaceOf`: the key without "-", `iso14001`, or `iso14001_…`); no sub-item fields, library items or automations on sub-items; links of extension items go through a link field the entry adds (to the pack's own items) or through a link field the sheet has (to items this pack adds to that field's target); a two-way link between an own sheet and a required pack's sheet needs its inverse in that sheet's extends. `extendsAgainst` checks an extension against the required pack's manifest (the catalogue tests): the sheets, groups and field keys it uses exist and new keys are new.
- **Planning:** each foreign sheet the pack reaches into (extends targets, link targets, action sheets) becomes a virtual sheet of the template (its live columns, with the options added, and groups) so the template planner resolves keys, `$option:` tokens, links, inverses and automations as for the pack's own sheets; then the virtual rows are swapped for the real ids and only what the extension adds is written: columns after the sheet's last (system columns), groups, views (`<pack>:<sheet>.view.<n>`, the standard view `.view.standard`), forms, example items (numbered by that sheet) and links. Options: `options` and the standard's option merge by id (an id already there is left as it is) into `plan.options` (ref map `option:<pack>:<sheet>.<key>.<id>`). A column key the sheet already has is a conflict. The snapshot (`PackSnapshot.foreign`, `foreignFolders`) carries the required installs' live sheets.
- **Ownership:** every row an extension adds has the extender's provenance and is in the extender's ref map, so the extender's upgrade and archive touch only its own rows.
- **Install order:** `requiredFirst` lists required packs that are missing or below the level the pack needs; `installPack` (and Create) install them first, each in its own transaction (`installRequired`), then plan the pack again. The preview says "Installs Core registers 1.0.0 (Starter) first." and lists what it adds to each register.
- **Upgrades:** an add-on's update adds new columns, groups, views, items and options to the Core sheets as for its own sheets (`upgrade_pack` accepts rows on required packs' sheets). A Core update that removes or retypes a field a live add-on uses (`extensionUses`: keys its views, forms, items, options, automations, formulas and lookups name) or drops a sheet it extends is **blocked**, naming the add-on.
- **Archive of an add-on:** its own sheets, dashboards and automations as for any pack; on the Core sheets its columns are archived (restorable), its views removed, its groups removed when empty (kept with items), its standard's option taken out of the Standards fields (items keep the id; installing again brings the tag back). Options it added elsewhere stay (items may use them). No shared row is deleted: items it added and items tagged with its standard stay with their history. The confirm dialog says so.
- **Hosted:** apply migration 0040, then load the catalogue (`scripts/packs-sql.ts`: `core` 1.0.0 and `iso-14001` 1.0.0).

## Bundles: ready-made sets from Create

The Create wizard's "Solve a problem" (docs/05 §4 Create) offers the catalogue's packs (frameworks excepted) as **ready-made sets**: the same manifest, planner and `install_pack`, with four additions. Owners and admins create them, as for packs; members see the set and its preview with "Ask an admin".

- **Parts.** `bundleParts` (`src/engine/packs/select.ts`, pure) lists the manifest's sheets, forms, automations and dashboards at the chosen level, with what each needs: a form its sheet; an automation its sheet, the sheets its actions name and the form that starts it; a dashboard the sheets its widgets read; a sheet the sheets its link fields point at. Leaving a part out leaves out everything that needs it (`togglePart` says what, and ticking a part brings back what it needs); `selectManifest` is the manifest as chosen: those parts gone, folders nobody uses dropped, setup steps on a left-out sheet dropped, the folder choice applied (its own folders, an existing folder by name, which the planner reuses, or none; a pack with a restricted folder keeps its folders). Apps stay as written: a screen whose objects the install lacks is not shown (docs/13). The server closes the exclusions again whatever the browser sent.
- **Safety.** A public form is flagged in the preview (forms install as drafts, so nothing is public until an owner or admin publishes it). An automation with an action that sends data out of the workspace (`OUTBOUND_ACTIONS`: webhook, email) is flagged and installed off whatever the manifest says. The preview says who can see each sheet (restricted ones: you and the owners).
- **Name, owner, review.** `create_bundle(org, plan, { name, owner_id, review_by })` (0038) runs `install_pack` and stamps the install with `bundle_name`, `owner_id`, `review_by` and `origin = 'create'` in the same transaction, then logs `bundle.created` on the workspace chain with the note "created via Create from <pack title> <version>". Owners and admins only; the owner must be a member; a level is never added this way (use Workspace admin › Packs).
- **Not yet reviewed.** Every sheet of a live set shows "Created by <name>" and, until the named owner presses Mark reviewed, "Generated from template, not yet reviewed" with the owner and the review date. `mark_bundle_reviewed(install)` accepts only the named owner, once, stores `reviewed_by` / `reviewed_at` and logs `bundle.reviewed`; the badge then reads "Reviewed by <name> on <date>".
- **Archive the whole set.** Owners and admins archive a set from any of its sheets ("Archive the whole set", an inline confirm): `archive_pack`, as above. Items and the activity log are kept.

A set is a pack install like any other: it shows under Workspace admin › Packs, upgrades as in Upgrades below (parts left out at create come back as additions there) and is created once per workspace (the wizard opens the existing one instead). The incident and internal audit starts ship as `start-incident` and `start-audit` 1.0.0 for this; a hosted catalogue needs them loaded (`scripts/packs-sql.ts`).

## Upgrades (P6)

A version is written once (change a pack, raise its version), and the catalogue keeps every version an install points at. A live install whose pack has a newer version in the catalogue shows **Update available x → y** on Workspace admin › Packs (installed packs) and, for an adopted framework library (`framework-<key>`), on Workspace admin › Frameworks. Owners and admins open the update dialog.

**The three-way diff** (`planPackUpgrade`, `src/engine/packs/upgrade.ts`, pure). Each object is matched by its stable ref through the install's `ref_map` and compared three ways:

- **base**: the installed version's manifest (read from the catalogue by the install's version; `pack_installs.manifest_hash` checked), planned as `install_pack` wrote it, with the plan's ids swapped for the install's;
- **mine**: the object as the workspace holds it now (read with the person's client; what they cannot read counts as removed by them and is left alone);
- **theirs**: the new manifest, planned the same way at the installed level (a level the new version dropped falls back to its lowest).

Per attribute: the pack did not change it → nothing; the client did not change it → the pack's change is applied; both changed it to different things → a **conflict**. Example items compare against what the install wrote (their `item.created` entry), so `$today` and `$in:N` values never read as changes; values merge field by field, so answers the pack never sets (status, owner, applicability) are never touched.

| Object | Compared | Rules |
|---|---|---|
| Folder | name | Removed from the pack: archived when nothing live is left in it |
| Sheet | name, description, item label | Removed: archived (restorable) only when it holds no items the client added and no example item the client changed; otherwise kept |
| Field | name, description, required, locked; settings key by key | **Add-only**: never a new type (a type change is kept and said), never removed (kept and said), options merged: the client's options stay in their order with their labels and colours, an option the client left as shipped takes the pack's new label and colour, new options are added, an option the client removed does not come back. New fields go after the sheet's last field |
| Group | name, colour | Removed: kept (it holds items) |
| View, form | name, settings | Removed: kept (views cannot be archived) |
| Example item, document | name, group, each value the pack sets | Removed: archived only when untouched since install; otherwise kept |
| Library requirement | the same | Rewords titles and the locked Purpose, Guidance, Audit questions and Typical evidence; new requirements are added with their requirement key; a requirement is never removed. Applicability, justification, status, owner and evidence are the client's |
| Automation | name, trigger, conditions, actions | The on/off state is the client's and never changes; removed from the pack: turned off |
| Approval workflows of a sheet | the sheet's `workflows` list as one value | Applied when the client left them as shipped; a conflict when both changed them (Keep mine / Take the pack's). Written after the rest in the same transaction (`update.workflows`, `apply_pack_upgrade`, which the app calls instead of `upgrade_pack`); approvals in progress keep the copy of the definition they started with |
| Dashboard | name, widgets | Removed: archived when untouched, otherwise kept |

New objects are added as an install would add them (new sheets with their folder, fields, groups, views, forms, items and links; positions after what the workspace has; a taken ID prefix is renamed and said). Links are added only from an item or through a field the update adds; links the client made or removed stay as they are. Sub-items are not added to a sheet that already exists (said, with the automations that need them). Client-added objects (no provenance) are never touched.

**Dry run and apply.** `previewPackUpgrade` plans on the server and returns the preview: added, changed, archived or turned off, kept (with why), conflicts and warnings, and the counts. The dialog shows each conflict with **Keep mine** (the default) or **Take the pack's**. `upgradePack` plans again from the catalogue and the workspace as they are now with those choices (the browser sends only the install, the new version's hash and the choices; a changed catalogue is refused) and calls `upgrade_pack(install, plan)` (0035): owners and admins, the plan for the version and hash installed now, only the install's own rows updated (only the columns the plan names; an option removed or a sheet with client items archived is refused), added rows with the install's provenance, new library items stamped with their requirement key (checked against the catalogue and the item's Ref), every item change logged on the item's chain (note "Pack update"), structure changes by the schema audit, and `pack.upgraded` on the workspace chain with the old and new version, the counts and the summary of conflicts. The install moves to the new version and hash and its ref map grows. One transaction: any failure leaves the workspace as it was. The result toast says how many objects were added, changed and archived and how many conflicts were kept.

## Frameworks

A framework's requirement library is a generated pack (docs/12): `frameworkToPack` (`src/engine/frameworks/pack.ts`) turns a framework file into a manifest with one library sheet (key `framework-<key>`, or `framework-<key>-<version>` for a later edition so both editions install side by side; version `<edition>.<revision>.0`). An update offers a new revision of the same edition only; a new edition is adopted and moved to (docs/12 Moving to a new edition). The sheet carries `framework: { key, version, refFieldKey }` and each item a `requirementRef` (`<framework>@<version>#<ref>`). The seed writes these packs with the others and then the requirement catalogue (`syncFrameworks`). They are not listed under Packs and `previewPack` / `installPack` refuse them: a framework is adopted from Workspace admin › Frameworks, through `adopt_framework`, which calls `install_pack` and stamps the requirement keys in the same transaction. An adopted library is archived like any pack (Installed packs › Archive).
