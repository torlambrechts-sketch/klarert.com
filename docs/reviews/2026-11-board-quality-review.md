## Verdict

- **Security:** no path lets data cross between workspaces, every table has RLS, every SECURITY DEFINER function sets search_path, the service role is used only in the allowed places, and anonymous visitors can call only `get_public_form`. But several rules are enforced only in TypeScript, so an editor calling the API directly with their own token can get round them. **3 High findings can expose data** (below). They must be fixed before real customer data goes in.
- **Usability:** the craft is good. Tokens are used throughout, icon buttons are labelled, and loading, empty and error states exist. It does not yet feel simple: the menu has 6 groups, there are 3 ways to start a sheet, Home stacks banners and setup cards, pack vocabulary (add-on, Core, Full, test mode) leaks into the UI, and invites have to be copied by hand.
- **Compliance:** the audit machinery is unusually strong: a hash-chained log, the SoA, the audit pack, edition-aware libraries, and the licensing rule is respected. The product is not yet a system of record for certification: document control stops at files plus approval, there is no read-and-accept, the SoA cannot be frozen, and internal audit and management review have no gates.
- **Operations:** CI on main has been red for most runs, so e2e did not run there. One hosted database is used for both the app and pgTAP runs. The scheduler and large exports will not scale.
- **Product:** the data-driven core (packs, apps, approvals) is a real differentiator. To sell it, the product still needs email notifications, policy lifecycle with attestation, SSO and MFA, an API, and billing.

## Appendix: security-db

### Board review: Security and privacy (DPO), data layer (security-db)

Reviewer: persona 6, Security and privacy / DPO, acting as database security reviewer.
Scope: `supabase/migrations` 0001 to 0049, `supabase/tests`, and the server code that decides what the database is trusted with (`src/server/automations/effects.ts`, `src/server/commands/{files,automations,forms,fields}.ts`). Read-only review at `780d779`. Nothing was run against a database. Every finding below comes from reading the code. Where I could not prove something, it is marked "unconfirmed".

## 1. Verdict

1. The tenancy and access model is careful and mostly sound. Every table has RLS, every SECURITY DEFINER function pins `search_path`, no `_` helper is granted, anonymous visitors can call only `get_public_form`, and restricted fields, personal-data masking and the append-only chain are designed with real care.
2. The sharpest gap: `sheets.org_id` and `fields.org_id` can be changed. Any editor can move a field or a whole sheet into a workspace they create themselves. That removes field restrictions for everyone, and it takes the sheet away from its workspace together with its history (H1). Separately, any editor can add themselves to a protected field's allow-list (H2).
3. Several rules live only in TypeScript commands, so a signed-in member calling PostgREST directly can get round them: automation target sheets, retention rules, direct `files` inserts, download logging, and links and files of restricted fields. Close these in the database before calling the product "no data-exposure flaws".

## 2. Findings

Severity is about real exploitability: a signed-in member of another workspace, a member with a lower role or restricted access, or an anonymous visitor. "Direct API" means PostgREST or Storage called with the public anon key and the person's own session. Supabase allows this for every signed-in person.

## 3. What is good

- One access resolver (`_sheet_levels`) used by policies, guard triggers and RPCs. Guard triggers on the written tables mean old and new RPCs alike obey sheet restrictions.
- Restricted values move out of `items.values` into their own RLS store, so Realtime, search, filters and the grid cannot leak them by accident.
- Masking before the chain with salted markers (restricted and personal), and erasure that nulls the salt so the chain still verifies. This is an elegant answer to "append-only versus Art. 17".
- Migration 0008 (no EXECUTE unless granted) and the explicit grants that follow it in every migration.
- Public forms: service role only, a reviewed privacy notice before a form can open, consent stamping, no IP stored, and prefill set on the server.
- Approval workflows: approvers fixed at submit, decisions insert-only, self-approval blocked.

## 4. Top 5 improvements, ranked

1. **Freeze tenancy columns (H1).** Make `org_id` immutable on every table, make `sheet_id` immutable on fields, groups and views, check the parent's org on insert, and make `hidden_field_ids()` independent of org. Add pgTAP tests that PATCH `org_id` as an editor. One small migration.
2. **Close command-only rules in the database (H2, M1, M4, M7).** Admin-only protected allow-lists, revoke direct writes on `files`, `automation_pauses` and `protected_values`, validate automation targets in SQL, and guard `settings.retention`. Then adopt one rule: *every rule in docs/02 has a database enforcement and a pgTAP test that calls PostgREST-equivalent SQL as `authenticated`*.
3. **Field visibility in every definer RPC that takes a field or file id (M2)**, and storage policies that mirror `download_file`, with mandatory access logging (M3).
4. **Fix chain ordering (M5)** with a per-chain sequence assigned under the lock, plus a concurrency test. An audit product cannot raise false tamper alarms.
5. **Complete erasure coverage (M6).** Mask comments, sub-item names and member names, and fold `restricted_activity` into erasure. Re-check automation creators at run time, so that offboarding really ends a person's data flows (M1b).

## 5. Gaps for a complete compliance system (privacy and security angle)

**Missing for GDPR and ISO 27001 at the data layer:**
- **Workspace deletion and export.** `app.purge_org` is honoured by the append-only triggers, but no purge function exists, and deleting an `orgs` row would fail on `activity_log`. Customers need a documented, logged workspace export (Art. 20, exit) and a purge with a retention grace period.
- **Data subject requests (DSAR).** There is a way to erase, but no way to *find*: a "where does this person appear" search across personal fields, names, comments, files and the log, with a DSAR register (due date 30 days, logged outcome).
- **Records of processing (RoPA), breach register, DPIA.** These should ship as packs on the core: the data-flow record (0049) is a good start. Add a breach log with a 72-hour clock field and notification automations.
- **Access reviews.** A periodic "who has access to what" export per sheet and field (`sheet_access_info` already has the data), plus an attestation item per review.
- **Key and secret hygiene.** Protected values are stored in clear in `protected_values`. Consider pgsodium or Vault column encryption, or at least say in the UI that they are access-controlled rather than encrypted.

**Document and policy editing, linking and creation: recommendation.** Yes, it belongs in the product, built on the existing core. The documents register (0023: approval workflow, author is not the approver, file versions, superseded marks) and approval workflows (0040) already cover the *controlled* half. What is missing is authoring in the app and read-acknowledgement. I would add:
1. A **policy document field or item body**: rich text stored as versioned rows, never edited in place. Each approved version gets a sha-256 in the item's chain (as `file.approved` does), so "what did the policy say on 3 March" is provable.
2. **Attestation**: an `ack` campaign that sends each published version to a group and records who read which version and when (the `ack` field type exists).
3. **Linking**: policies ↔ controls ↔ requirements through the existing `controllink` / `requirement` links. Reuse the library model.

Security conditions for doing it: sanitise rich text on the server (allow-list HTML or Markdown only), apply restricted-field and sheet rules to document bodies, and treat document bodies as personal data where `personalData` is set. Never ship standard text (docs/12 licensing): templates must be our own words.

## 3. What is good

- Document approval is real: only a person approves, never the author (creator), needs a version note and a file, blocks scan-blocked files, logs `file.approved`, and an approved doc cannot start approved (`0023_item_files.sql:257-410`; workflow in `0040`).
- Audit pack: SoA per library, registers, evidence index with SHA-256, activity log and chain verification, period filter, restricted values masked, every export logged (`docs/11-packs.md:252-260`).
- Hash chain with per-chain advisory lock and append-only trigger (`0001_core.sql:289-309`), personal-data redaction by salted markers that keeps the chain valid (`docs/02 §18`).
- Auditor role with a mandatory expiry date, enforced in every policy (`0025`).
- Framework model: edition status and transition dates, edition mapping with a "move" that copies only one-to-one equivalents, cross-walks conservative by default, Not applicable needs justification, "undecided" counts as in scope (honest).
- Licensing rule is followed in the data: titles and numbers only, own-words guidance, audit questions and typical evidence that read as auditor-useful.
- CAPA gate: closing needs root cause and effectiveness check, plus a CAPA closure workflow (`core.json` nc rules).

## 4. Top 5 improvements, ranked

1. Make ack and signature trustworthy on the server (C-01), then build publish and read-and-accept on top of it (C-02).
2. Freeze and approve the SoA as a versioned record (C-03).
3. Put gates on internal audit and management review, with findings and decisions linked to NC/CAPA and Actions (C-04, C-07).
4. Correct coverage so it cannot overstate (C-08), and add evidence review and sampling (C-14).
5. External anchor of chain heads and a manifest hash in the audit pack (C-06, C-16); in parallel mark the unverified 2026 editions (C-05).

## 5. Gaps for a complete compliance system, and document and policy editing

**Does it belong in the product? Yes for the lifecycle, no for a general word processor.** An auditor's question is never "where is the file" but "which version was in force on date X, who approved it, who was told, and what does it control". The product already holds approval, review dates, register and requirement links; the missing pieces are authoring, publication and acceptance. Without them the system of record is a file cabinet, and customers will keep a parallel spreadsheet.

Recommended order (each step builds on the earlier one):

1. **Trust fix (C-01).** Server-enforced ack and signature, version-reset rule, `v<n>` format (C-17). Prerequisite for everything below.
2. **Publish and read-and-accept.** On an Approved document version: audience (people, teams, job titles), "Publish" sets an effective date, creates one acknowledgement task per person (My work), due date, reminders and escalation through existing automations, and a per-version acceptance report exportable to the audit pack. New version resets. This answers 7.5.3 distribution and 7.3 awareness.
3. **Linking.** Documents already link to requirements; add links to controls, risks, processes and training; a "Documents that cover this requirement" and "Requirements with no document" report. Obsolete handling and supersedes link (C-10).
4. **In-app editor and templates.** A structured, versioned rich-text body (headings, tables, change log) stored as the document version, with the pack ship own-words templates (information security policy, access control, supplier, BCP, DPIA). Approval workflow works on the body, with a diff from the previous version and PDF render on publish. Keep Word/PDF upload as a first-class alternative; do not build real-time co-editing or track changes.
5. **Policy exceptions register.** Policy, requestor, risk, compensating control, approver, expiry date with automation; links to the Risk register (risk acceptance already exists).
6. **Audit programme and calendar.** Annual programme: audits by process and clause, coverage report ("clauses not audited in this cycle"), independence check, checklist from the framework's audit questions (already shipped in the library), findings to CAPA.
7. **Training and awareness records.** Competence matrix and evidence (C-11), generated from acknowledgements and course completions.
8. **KPIs and objectives readings (C-12).** Readings and trend, feeding the management review inputs.
9. **Supplier questionnaires.** Supplier management already has requirement checks; add a questionnaire template and a scored response, sent by the public form route (needs the security persona's review, because it extends the public surface). Last, because it adds an external surface.

Do not build: a full DMS with folders and check-in/check-out, e-signature with identity proofing, or an LMS. Link to them instead.

## 5. A complete compliance system: document and policy editing

**What exists.** A documents register (`src/engine/documents.ts`, docs/02 §14) with versioned files, approval enforced in SQL, approval workflows (0040), the hash-chained log, `ack` (read and acknowledge), `signature`, `version` and `requirement`/`controllink` fields, and `item_links` for linking. **Recommendation: yes, build in-app authoring, but as a field type on the existing documents register, not a separate docs product.** This fits rule 1 ("data, not code").

- **A "document body" field type** (`engine/fields/docbody.ts`): rich text stored as ProseMirror/TipTap JSON (sanitised; schema checked with Zod). The editor is lazy-loaded only in the item panel, so the grid bundle does not grow.
- **Approval freezes a version.** On approval, the server renders the body to PDF/HTML and stores it as a new **file version** of the item. The existing approval, download and audit-pack paths, and the hash chain, then cover authored documents with no new audit code. Drafts are edited; approved versions are immutable.
- **One editor at a time in v1** (the existing item lock and edit hold, plus `expected_updated_at` once E11 is fixed). Do not build real-time co-editing (Yjs or CRDT): it costs L+ and it is not what auditors ask for.
- **Linking:** clause and control references inside the body become `item_links` (policy ↔ controls ↔ risks ↔ requirements), so the SoA and coverage views count them.
- **Templates come from packs as data**, in our own wording only (docs/12 licensing rule: never ISO/IEC text).
- **Read acknowledgement** reuses the `ack` field, plus a scheduled re-ack on each new version.

Cost: about M–L (editor, sanitising, PDF render on the server, tests). Do it **after** E1–E5. Authored policies make the audit pack and the scheduler more central, which are exactly the paths that are fragile today.

## 3. What is good (and differentiated)
- Data-not-code packs, add-ons on shared Core registers (a risk is recorded once and counts for every standard). Vanta and Drata cannot be reshaped by a customer; monday setups have no standards content. This is the main differentiator.
- Audit trail that holds up: hash-chained, append-only, with Verify, personal-data redaction without breaking the chain (docs/02 §327), and logged exports. Few competitors can show an auditor this.
- Approval workflows, the document approval rules (author never approves, version note required, approved file tracked and superseded) and the SoA, audit pack zip and management review inputs: the things an ISO auditor actually asks for.
- Cross-walks between frameworks and the licensing discipline (no ISO text), EU residency, field-level restriction, auditor role with an end date, and the data-flow record ("what leaves the system"): privacy-buyer features that cost others a lot to add.
- Test-mode for notifying automations and the Design view: a customer can see and trust what automation does. Rare at this size.

## 4. What to cut or hide to stay simple
1. Hide 57 field types behind the 12 essentials plus search (the spec already does this); do not advertise "57 types" in marketing. Customers buy outcomes.
2. Hide the Design/Map explorer and the automation builder under an "Advanced" flag for non-admins. They serve consultants and admins, not the compliance owner.
3. Launch with three standards (ISO 27001, GDPR, NIS2) plus Core and Supplier management. ISO 9001, 14001 and 45001 stay in the catalogue but out of the default Create list until a customer asks.
4. Do not build: a free canvas (already rejected), a built-in LMS, a general document editor, AI generation beyond a drafted answer, a connector marketplace, mobile apps.
5. Keep sheets and spreadsheet freedom for admins and consultants, but give the compliance owner an "app" front door (docs/13): Today, My work, Documents, Audit-ready. Most buyers should never see a sheet's field settings.

## 5. Document and policy editing, linking and creation: do they belong?
**Recommendation: yes for policies, no for general documents.** Build a thin policy lifecycle on the existing documents register; do not become Google Docs.

What exists: a controlled documents register with file versions, approval (a person, not the author, with a version note), supersede, review-date automations, links from any item to documents, and a default set of ISMS and GDPR draft documents in the packs. What is missing is writing, publishing, and proof that people read it.

Proposed shape, in order:
1. **Policy body as structured text in the document item** (a long-text/markdown field with headings, not a free-form editor), plus "Export to PDF" on approval, which becomes the controlled file. Authors keep using Word if they prefer: upload remains the primary path. The pack drafts ship as starting text written by you (no standard text, per docs/12).
2. **Templates and variables**: `{company}`, `{owner}`, `{scope}` from workspace data, so one policy set renders for each entity or client. This is where consultants will pay.
3. **Publish and attest**: approval publishes the version; an audience (teams, job roles, everyone) gets an assignment (inbox plus email, F-01); each person clicks "I have read and understood" (the `ack` field already stores user, time and version); a new version resets and re-assigns. Report: % attested per policy, who is late, exportable for the auditor.
4. **Linking** is already the right design (policy to control, requirement, risk, supplier). Add a reverse "Policies for this requirement" panel in the requirement item, and a coverage check "requirement has an approved, in-date policy".
5. **Reviews**: review due dates and escalations exist; add "no change needed, reconfirm" as one click that writes a new review date and a log entry.
Out of scope: co-editing, tracked changes, comments inside text. If a customer needs those, integrate with M365 or Google Docs (store a link plus a PDF snapshot on approval).

## 5. Documents and policies: do they belong in the product?
How clients work today: nearly all keep policies in Word on SharePoint or Google Drive. Staff already read them there, legal and HR edit them there, and the auditor accepts a PDF. They do not want to retype a policy into a new editor. Their pain is not editing; it is control: which version is current, who approved it, who has read it, which controls and requirements it supports, when it is next reviewed.

Recommendation, in order:
1. Yes, in the product: control, linking, reviews and attestations (what exists, plus C3 and C4). The register, approval workflow, review date automations and links to requirements already exist. Link documents to framework requirements ("evidence for 5.2 and A.5.1") so the SoA lists the policy by name and version. Docs/12 already lists linked evidence, so confirm documents can be linked into a library item as evidence. Unconfirmed.
2. Yes, creation from templates: a "New document from template" that copies a starter body, fills ID, owner, version and review date, and starts the workflow. Templates must be own words (docs/12 licensing).
3. A light in-app editor for the policy body (headings, lists, tables, no layout engine), stored per version, exported to PDF and DOCX, with the approved version frozen and hashed. Offer it as an option, not a requirement: a client that wants Word keeps the file and the register points at it. Build only after items 1, 2 and attestations. A full collaborative editor, track-changes and SharePoint sync should stay out of the MVP; offer a Drive or SharePoint link field as the cheap bridge.
4. Docs are silent on all of this (no editor, no template, no body field in docs/01–13), so it is an owner decision, not something to invent.

Other gaps for a complete system, by priority: nonconformity and audit workflows exist; missing or unconfirmed are an internal audit checklist and finding flow per clause (docs/06 lists audits register only), competence matrix beyond a training register, and management review minutes sign-off (inputs are compiled, docs/11:255).
